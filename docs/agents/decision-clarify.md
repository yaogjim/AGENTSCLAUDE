# 决策请求的解释义务（细则）

> 母版细则文件，随母版全局加载生效，不拷贝到项目。核心规则见母版 AGENTS.md §2「决策请求的解释义务」。

## 适用分级

- **重决策**（按下节完整六要素说明）：不可逆或回退成本高；改变业务语义、数据模型、权限或对外契约；涉及真实业务数据、生产环境、secret 或外部授权。
- **常规技术选型**（三要素即可）：每个选项的准确含义、推荐项及依据、是否可逆。讨论中发现选择会影响业务语义、数据或权限时，升级为重决策。

## 重决策的六要素

提出选项前，必须先用用户能够核实的语言说明：

1. **决策对象和触发原因**：现在要决定什么，为什么必须在此时决定，哪些代码现实、业务规则或外部条件造成了分岔。
2. **每个选项的准确含义**：分别说明在正常、异常、重试、人工介入和回退场景下，系统、数据、任务和用户会发生什么变化。
3. **适用场景和具体例子**：至少给出一个典型业务场景；复杂状态或多消费方决策应使用简明对照表、流程或示例，不能要求用户自行推断后果。
4. **收益、成本和风险**：短期收益、长期维护成本、数据与权限风险、失败影响、是否可能阻塞后续流程，以及决策是否可逆、如何回退。
5. **推荐意见和依据**：明确推荐哪个选项、推荐成立的前提及不推荐其他选项的关键原因；不得用模糊措辞或省略重要代价来诱导选择。
6. **选择后的执行边界**：说明用户确认后会更新哪些需求/设计/计划、是否涉及迁移或外部授权、何时才会开始实现和验证。

## 通用规则

- 选项必须互斥、可执行且使用一致的比较维度。
- 一次只请求一个聚焦决策，等用户答复后再提下一个。
- 用户确认后，先把选择重述为无歧义的业务规则，同步 PRD、Design、Plan/Roadmap 和活动 Todo，再按已确认计划进入实现。
- 不得把聊天中的编号选择直接当作足够的实现规格。
