# 执行模式与闭环交付（细则）

> 母版细则文件，随母版全局加载生效，不拷贝到项目。四种执行模式的定义见母版 AGENTS.md §2「执行模式与完整闭环交付」。

## 完整闭环交付的定位

「完整闭环交付」是一种执行模式，不是所有请求的默认模式。它只在用户明确授权进入执行，且目标、范围、验收口径可判断时触发。目标是防止计划很好但执行不到位，而不是扩大范围、跳过确认或替用户做未授权决策。

用户已明确确认的需求、设计、范围和执行授权不再重复等待确认；任一项不完整，或与当前代码、文档、数据、环境现实冲突时，回到规划/确认流程。

本细则受 AGENTS.md §1「执行原则」与「越界处理」约束：只推进当前已授权范围内的必要工作，满足验收标准后立即停止，不追加优化、扩展或清理；范围外问题只报告、不处理。必要的验证与文档收口应纳入本次验收，不作为验收后继续工作的理由。

## 触发与不触发

按闭环处理的典型口径（含等价表达）：

- "请按完整闭环交付处理这项工作" / "计划确认后请连续推进到验证和文档收口"
- "前面讨论的需求、设计和范围我已确认，请直接进入执行"
- "除非遇到授权边界、生产语义、真实数据安全、secret 或不可逆操作，否则连续推进"

默认**不触发**（除非用户额外明确授权执行）：

- 仅要求分析、反思、评审、比较、解释、规划或设计。
- 用户要求"先整理""先给方案""等我确认""不要写入""不要实现"。
- 需求、范围、验收标准、生产语义、真实数据边界或产品决策仍不清楚。
- 需要新增长期产品能力、改变核心业务规则、改动真实数据、使用 secret、执行不可逆操作。

不触发代码执行不等于免除质量门禁：用户明确要求方案、设计、架构，或要求缺少已批准 Design 锚点的复杂实施计划时，仍须按 AGENTS.md §2「设计现实校准与关键决策闭合」做只读取证并通过 [doc-quality.md](doc-quality.md) 的 Design Gate。承重事实未知时可先执行范围明确的只读 probe/spike；它只产出证据与设计结论，不授权功能代码、schema、数据、权限或对外契约变更。

## 闭环执行顺序

1. **目标命题落地**：先写清本次要证明什么——业务结果、交付对象、运行路径、验收证据和非目标范围。
2. **现实校准**：读取当前代码、文档、配置、测试和运行环境；发现与已确认计划冲突时，先暂停说明。
3. **小步实现**：按 AGENTS.md §1 的 TDD 与 Tidy First 推进（结构性变更与行为性变更分开处理）；优先使用隔离测试数据和既有命名空间，不污染真实数据。
4. **调用链接线**：新能力必须能从真实入口走到真实输出（AGENTS.md §5「接线即交付」）；函数存在但未接入主路径，不得视为完成。
5. **按风险验证**：按变更风险与验收标准选择必要的单元、集成、契约、API、DB、E2E、浏览器、日志、审计或导出验证；窄改动跑相关测试，共享模块/跨流程改动仅在影响面确有需要时扩大测试；涉及 Web UI 行为变更时做受影响路径的浏览器验证。不机械叠加全部检查，不做无明确收益的重复验证。
6. **文档收口**：同步更新对应 PRD、Design、Plan、Roadmap 或测试矩阵，状态必须与证据一致。
7. **缺口登记**：无法完成的问题分类记录为 `feature-gap`、`test-gap`、`data-gap`、`env-gap`、`permission-secret-gap` 或 `product-decision-gap`。

## 暂停条件

执行中遇到以下情况必须暂停并请求确认：

- 目标、范围、验收口径或业务语义无法判断。
- 需要改变已确认的产品规则、权限规则、数据模型或对外契约。
- 涉及真实业务数据、生产环境、secret、不可逆操作或高风险迁移。
- 现有代码能力不足，继续执行会把 mock、fixture、dry-run、截图或局部测试误当成真实业务完成。
- 完成当前任务确需超出本次授权范围的改动，不以扩大幅度大小判断是否需要确认。

在已授权范围内，能合理判断的问题应连续推进到收口；一旦出现上述任一情况，必须停下来澄清。需要越界时，按 AGENTS.md §1「越界处理」说明当前范围内无法完成的原因、必须增加的改动、最小可行方案及其影响，获得确认后再继续；不影响当前任务验收的范围外问题只报告，不因此扩大任务或阻塞收口。

## 收口前反向审计

宣称完成前，仅针对本次变更与验收相关项核对已有证据；证据充分时不重复运行检查，不扩展为全仓审计：

1. 本次目标命题是否已经逐项被证据证明。
2. 证据对象、环境、数据、角色、版本是否与声明一致。
3. 是否存在未接线代码、孤儿测试、过期文档或 ignored 报告。
4. 是否把中间产物（AGENTS.md §2「禁止跨对象借证据」所列）误当成业务完成。
5. 剩余缺口是否已分类记录，并明确是否阻塞本阶段验收。

## 收口说明要求

最终说明必须包含：

- 完成了什么。
- 验证了什么，列出关键命令和 API/UI/DB/E2E/browser 证据。
- 发现并修复了什么问题。
- 哪些内容没有完成，属于哪类缺口。
- 当前状态是 `accepted` 还是 `verified-partial`，不得含糊。
