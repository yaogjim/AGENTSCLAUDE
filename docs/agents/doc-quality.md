# 文档体系与质量（细则）

> 母版细则文件，随母版全局加载生效，不拷贝到项目。文档路径映射见母版 AGENTS.md §3 默认表与项目 project.md 声明。写 PRD / Design / Plan / Roadmap 前，先读本文件对应小节。

## PRD 质量要求

PRD 必须能回答：用户是谁、痛点是什么、做什么、不做什么、输入输出是什么、验收标准是什么。章节编号不固定，但凡包含"用户与场景""用户故事""功能需求""端到端用户故事/场景化功能串联"等内容类型，都必须有足够上下文和场景化表达：

- **用户与场景**：不能只列角色表格，应说明用户在什么业务链路中进入系统、当前卡点是什么、系统如何帮助其推进目标。
- **用户故事**：不能只是孤立短句，应按主要场景分组，说明故事发生的上下文，并尽量关联功能需求 ID，使场景、故事和需求可追踪。
- **功能需求**：不能只写功能名和一句验收标准；应说明用户价值、触发场景、关键输入、关键输出、核心规则、边界，以及可验证的验收要点。必要时使用文字流程图或 Mermaid 流程图辅助说明。
- **端到端用户故事/场景化功能串联**：用于让系统活起来、串起来、流动起来。复杂功能或产品级 PRD 至少补充 1-2 个典型场景；每个场景说明背景、用户目标、用户如何一步一步完成目标、过程中触发哪些功能需求、输入输出如何流转、人工确认/失败/权限/审计等边界如何处理。

PRD 场景、功能和用户故事要丰满生动但不失精炼。所有内容必须基于产品体系规划、现有代码和已确认能力，不得把 mock、readiness、sandbox、规划中能力写成真实生产完成。

## Design 质量要求

Design 必须能回答：技术栈和现有能力如何复用、模块如何分工、数据和状态如何流转、失败如何恢复、关键取舍是什么。复杂功能还必须达到**实施级 Design**：会影响业务语义、数据正确性、接口兼容、执行顺序、失败恢复、安全权限、迁移回滚或用户可见状态的关键决策已经闭合；实现者只需决定不改变外部契约和运行结果的低层实现细节。

篇幅、章节数量、代码块或图表数量都不是质量指标。普通功能按风险和适用性精简填写；复杂功能不得以“保持简洁”为由省略关键合同。不适用项可在适用性摘要中合并标记 `N/A` 并说明原因，不为每项生成空章节或机械填表。

### 设计前现实校准

形成设计结论前，先建立最小取证记录：

1. **权威来源**：列出适用的 PRD、现行 Design/ADR、代码入口、数据结构、接口、配置、测试、部署/运行入口和外部依赖，并记录可核实的文件/章节/符号/版本锚点。
2. **现状与目标差异**：说明当前链路、可复用能力、已知缺陷、参考方案与当前仓库现实的冲突；不得把参考方案中的假设直接写成本项目事实。
3. **事实分级**：
   - `evidence_status=verified`：已从当前权威来源直接核实；
   - `evidence_status=inferred`：由多个已核实事实推导，必须说明推导依据；
   - `evidence_status=assumption`：尚未核实但暂用于比较方案，不得作为实施前提静默落地；
   - `evidence_status=unknown`：缺乏证据，必须说明影响、验证探针和阻塞范围。
4. **缺口分类与处理**：
   - `gap_type=fact-gap`：当前路由、schema、稳定键、外部能力、数据分布、运行限制等可被证实或证伪的经验事实。只能通过当前权威证据或只读探针消除；用户或负责人可以接受风险，但不能把未验证事实批准为 `evidence_status=verified`。无法直接验证时，只有设计显式覆盖全部可能分支并以运行时检测安全选择，才能消除它作为实施前提的阻塞。
   - `gap_type=decision-gap`：产品语义、架构取舍、权限政策、风险偏好等需要有权人选择的事项。按 AGENTS.md §2 决策流程确认并记录后关闭。
   - 会改变核心架构、数据模型、权限、对外契约、迁移或回滚方案的承重 `fact-gap`，登记为 `research-required` 并保持 `Design Readiness=not-ready`；承重 `decision-gap` 未确认时保持 `Design Readiness=review-required`。不得用伪代码、精确字段名、阈值或工期制造伪确定性。

声称“已有”“已支持”“当前调用”“可以直接复用”时必须有当前证据锚点。外部文档、历史方案和模型记忆只能作为候选证据，不能替代当前代码、配置、schema、测试或运行证据。

承重事实未知时，允许先建立只读 probe/spike 计划，写明问题、探针、退出标准、证据产物和假设不成立时的分支。该计划是取证工具，不是实施 Plan，不授权功能代码、schema 或对外契约变更。无 checkout 的概念咨询不假装完成仓库取证，只需说明材料边界、假设和如何在实施前验证。

### 实施级设计合同（按适用性）

每个独立方向、模块或纵向业务链路应使用稳定小节说明以下适用项，不能只在全局章节提一次后让实现者自行拼接。跨方向共享的合同可在一个权威章节定义一次，各方向用稳定锚点引用并只写本方向的适配与覆盖，不复制形成多份真源：

1. **问题机制、目标与约束**：从表面痛点追溯到根因、承重不变量或结构性矛盾，说明所选机制为什么能改变根因、在什么证据下会被证伪；再定义成功结果、范围、非目标、不可改变项、兼容边界和承重假设。字段齐全但没有“问题 → 根因 → 机制 → 可证伪结果”的因果链，不算完成设计。
2. **架构与模块职责**：模块、接口、调用方向、事实源、依赖及其放置理由；明确复杂性归属和禁止穿透的边界，避免只有方框图而没有职责合同。
3. **数据合同**：字段名与语义、来源、类型、必填/可空、默认值、枚举/单位、校验、身份键、比较键、唯一性、索引、生命周期、敏感级别及新旧字段兼容。身份键与比较键必须明确区分，并说明选择依据。
4. **接口合同**：API、方法、事件、配置或文件格式的调用方/生产者/消费者、输入、输出、错误语义、鉴权、幂等、分页/批量、超时、版本兼容及重试责任。仅列接口名称不算合同。
5. **规则与算法**：输入输出、标准化、匹配/排序/去重、公式或计算规则、边界、阈值、并列裁决和确定性要求；关键比较键、优先级和阈值不得留给实现者猜测。会影响业务结果的阈值、默认值和枚举必须追溯到当前证据、用户确认或明确标记的 proposal；proposal 在确认前不得进入实施。无法确认的值进入待决问题，不随意编造。
6. **执行与一致性**：不可交换的执行顺序、事务边界、原子性、锁、并发冲突、重复执行、超时、重试/退避、部分成功、补偿和最终安全状态；说明错误顺序或错误替代方案会如何失效。
7. **状态与生命周期**：状态定义、持久化位置、触发者、合法转换、转换前置条件、副作用、非法转换、取消/恢复/重开和终态。只给枚举名称不算状态机。
8. **失败与恢复**：按失败点说明检测信号、是否重试、数据是否写入、旧基线是否保留、清理/补偿、人工介入、告警与审计；明确“何时必须停止”，不能只写“异常时提示失败”。
9. **UI 与交互**：真实入口、信息架构、操作顺序、字段与动作，以及正常、loading、empty、error、stale、conflict、partial-success、disabled、无权限、编辑回显、取消和恢复状态；前后端状态与错误语义必须对应。无 UI 时标记 `N/A`。
10. **安全、权限、非功能与可观测性**：角色正反向权限、输入/输出治理、secret 和敏感数据、性能/容量/可用性目标与资源上限、审计事件、日志/指标/追踪、告警阈值与责任人；安全与非功能控制必须说明接在线路的哪个位置。没有相关风险或已由系统级合同覆盖时可引用并标记 `N/A`。
11. **迁移、兼容与回滚**：存量数据处理、新旧并存、Feature Flag、双写/双读（若有）、切换门禁、完整性断言、回滚触发条件、回滚步骤、切换后增量数据保护及旧路径退出条件。
12. **验证合同**：把正常、边界、失败、并发、权限、迁移、回滚和兼容场景映射到单元/集成/契约/API/DB/E2E/浏览器/运行证据；写明样本、环境、预期结果和可复现命令或证据产物。
13. **实施落点与追踪**：预计新增/修改/复用的文件或模块、需求锚点、ADR/设计决策、后续 Plan 切片和验收证据。文件清单用于证明接线落点，不代替架构设计。
14. **备选方案与未决问题**：记录采用方案、关键替代方案、选择依据、替代方案的失效方式、决策是否可逆；未决问题注明 owner、验证方式、影响和是否阻塞。

设计中的 DDL、DTO、接口签名、伪代码、线框图和时序图用于固化合同，不是为了展示“写得详细”。它们必须与当前证据和正文语义一致；没有依据的精确代码比明确的未知项更危险。

### 跨层一致性与引用规则

- 同一业务概念的名称、身份键、比较键、枚举、状态、错误语义和版本必须在数据、Service、API、Job、UI、迁移和测试中保持一致；若某层需要转换，明确转换规则与事实源。
- 每个关键需求都应有设计承接；Design 获批前，每个关键设计决策应明确预期 Plan 工作包、测试与证据承接点，禁止孤立字段、孤立状态和孤立接口。正式实施 Plan 仅在 `Design Readiness=approved` 后创建或定稿，并引用稳定设计锚点，不要求在 Design Gate 前先存在正式 Plan。
- 引用其他方案时必须写明固定路径或版本、具体章节/决策 ID、明确继承内容、本次覆盖内容和冲突优先级。仅写“按原方案”“直接继承”“复用现有能力”不能替代本次 Design 合同；Plan 应引用 Design 的稳定锚点，不复制 DDL、接口和状态机形成第二份契约。
- 参考方案若与当前代码或运行事实冲突，以当前核实证据和用户确认后的业务规则为准，并把差异写入 Design；不得静默选择一方。

### 客观 Design Gate

Design Readiness 是独立于 `todo.status` 和 `delivery_status` 的设计门禁，只使用以下三种状态：

- `Design Readiness=not-ready`：存在 `research-required` 证据缺口，或设计合同、异常路径、回滚、验证仍有关键缺口。
- `Design Readiness=review-required`：合同已闭合且自检通过，但仍有需要用户/架构/安全/数据负责人确认的重决策。
- `Design Readiness=approved`：所有适用项已完成或合理标记 `N/A`，阻塞决策已确认，且通过下述门禁；这只代表可以进入实施 Plan/实现，不代表功能已经实现。

复杂 Design 在环境具备评审者或子代理能力时，必须由未参与主要设计的评审者仅依据文档完成至少一次实现模拟；评审者不得依赖作者口头补充。环境不具备独立评审能力时，由作者执行独立的反向审计段落并明确记录“未做独立评审”，不能把自审表述成外部复核。

复杂 Design 必须保留一段可审计的 **Design Gate 记录**，至少包含：设计版本/锚点、评审者与时间、适用项及 `N/A` 理由、代表性正常链路、最高风险失败/并发链路、适用的迁移回滚链路、模拟中被迫临场决定的事项、阻塞缺口和最终 verdict。已接入项目写入 Design 或其评审记录；未接入项目可保留在当前设计交付物中，不因此强制创建文件。

以下触发条件不得被笼统标记 `N/A`：存在持久化写入时必须评估数据合同、一致性、失败恢复和回滚；存在外部接口/事件/配置时必须评估接口、错误、兼容和安全；存在 UI 时必须评估用户状态与权限；存在异步/长期任务时必须评估状态、并发、重试、恢复和可观测性；存在 schema/数据迁移时必须评估完整性、兼容、切换与回滚。只有已有系统级合同明确覆盖且给出有效锚点时，才可引用后标记本设计无需重复展开。

标记 `Design Readiness=approved` 前必须全部通过：

1. **问题机制门禁**：表面痛点、根因/承重不变量、所选机制、预期因果结果和证伪条件形成闭环，没有精确实现错误问题。
2. **现实门禁**：关键事实有当前锚点；承重 `fact-gap` 已验证或通过覆盖全部可能分支的设计消除为前提，承重 `decision-gap` 已由有权人确认；风险接受不等于事实成立，没有用精确措辞掩盖未知。
3. **合同门禁**：所有适用设计合同已闭合，关键 TBD、模糊动词和未定义枚举为零，`N/A` 均通过触发条件质询。
4. **正向实现模拟**：从真实入口逐步走到可观察业务结果，逐步核对输入、处理、状态、副作用、UI 和证据，无需临场补充关键决定。
5. **失败与恢复模拟**：至少走查外部依赖失败、重复/并发、部分写入或中断、权限拒绝、回滚中适用的路径，最终数据和用户状态明确。
6. **关键自由裁量测试**：两名合格实现者完全遵守文档时，不会在业务语义、数据结果、接口兼容、安全权限、迁移回滚或用户可见行为上产生互不兼容的实现。
7. **跨层一致性门禁**：数据、接口、状态、UI、迁移和测试使用同一套术语、键、枚举与错误语义，转换点已明确。
8. **承接与验证门禁**：需求、设计、预期 Plan 工作包、测试承接点和预期运行证据可追踪；正式实施 Plan 在 Design 获批后引用这些锚点，且证据对象与未来完成声明一致。

任一项失败时，不得通过压缩措辞、删除 TBD 或把问题移入 Plan 来获得 `Design Readiness=approved`；应回到取证、设计或用户决策。

### 紧凑正反例

| 低质量写法（拒收） | 实施级写法的最低形态 |
|---|---|
| “直接继承原方案的数据表和同步逻辑” | 指定原方案路径/版本/章节；逐项列出继承的 schema、键和护栏；说明本次覆盖、冲突优先级及当前代码核验结果 |
| “比较新旧数据，变化时标记失效” | 明确身份键、比较字段、变化分类、执行顺序、状态映射、异常停止条件、旧基线保护和验证样本 |
| “低置信度时人工确认” | 定义置信度来源、阈值或待决门禁、触发条件、人工可见证据、确认/拒绝副作用、重试和审计 |
| “失败自动重试并提示用户” | 按失败点规定超时、重试责任与上限、幂等、已写数据处置、最终安全状态、UI 状态、告警和人工恢复 |
| “新增管理页面支持配置” | 给出入口、对象和动作，及 loading/empty/error/stale/conflict/无权限/编辑回显/取消恢复状态与对应接口 |
| “阶段一完成底座，阶段二完成 UI” | Design 先闭合底座与 UI 的合同；Plan 再按依赖拆阶段，并逐项引用设计锚点、测试和回滚，不用阶段名代替设计 |

反例用于识别结构性缺口，不要求照抄右栏文字。真正标准始终是：关键决策是否有事实依据、跨层闭合并可被验证。

## Plan / Roadmap 质量要求

- Plan 先给出总阶段路线图，再写阶段详情；每个阶段覆盖"阶段六要素"（见 AGENTS.md §2「通用功能开发流程」第 6 步）。计划采用"阶段 → 功能模块 → 工作包 → 可执行切片 → 验收 → 测试 → 文档/回退"的分层执行文档，不以表格为主。
- Roadmap 提供全周期全景图，说明 Now / Next / Later 或 Phase 0 → Phase N 的递进关系。
- **路线图文档顶部必须按以下顺序优先放三块内容**：
  1. **完整功能链路状态**：先写用户目标链路，逐环节说明输入、输出、接线、验证和阻断，并给出整链最低状态。
  2. **完整路线图总览**：列出所有阶段、主题、当前状态和一句话说明。
  3. **下一阶段优先实施内容**：说明下一阶段补齐哪个链路环节、验收标准和风险，不要把下一步埋在长文末尾。

## PRD vs Design 边界

文档内容严格归位，分界以本节为准：

- **PRD**（What & Why）：产品定义、用户故事、功能清单（用户视角）、业务流程、用户交互流程、业务对象（概念层）、非功能需求、验收标准。不含技术栈、字段级模型、API 设计、内部算法。
- **Design**（How）：技术栈选择及理由、系统架构、数据模型（字段级定义）、接口设计、核心算法、系统执行流程、状态流与恢复流程、错误处理与安全、设计决策及备选方案否决理由。

## 顶层文档 vs 功能文档边界

- 顶层 PRD、设计、路线图文档只保留产品级、系统级和版本级摘要。
- 复杂功能的细节必须放到 `docs/features/<feature>/`，顶层文档只保留摘要和链接。
- 系统采用技术栈、全局架构图和全局模块边界放在顶层设计文档。
