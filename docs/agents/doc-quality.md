# 文档体系与质量（细则）

> 母版细则文件，随 AGENTS.md 一并拷贝，无需项目适配。文档路径映射见项目 AGENTS.md §3「文档映射关系」。写 PRD / Design / Plan / Roadmap 前，先读本文件对应小节。

## PRD 质量要求

PRD 必须能回答：用户是谁、痛点是什么、做什么、不做什么、输入输出是什么、验收标准是什么。章节编号不固定，但凡包含"用户与场景""用户故事""功能需求""端到端用户故事/场景化功能串联"等内容类型，都必须有足够上下文和场景化表达：

- **用户与场景**：不能只列角色表格，应说明用户在什么业务链路中进入系统、当前卡点是什么、系统如何帮助其推进目标。
- **用户故事**：不能只是孤立短句，应按主要场景分组，说明故事发生的上下文，并尽量关联功能需求 ID，使场景、故事和需求可追踪。
- **功能需求**：不能只写功能名和一句验收标准；应说明用户价值、触发场景、关键输入、关键输出、核心规则、边界，以及可验证的验收要点。必要时使用文字流程图或 Mermaid 流程图辅助说明。
- **端到端用户故事/场景化功能串联**：用于让系统活起来、串起来、流动起来。复杂功能或产品级 PRD 至少补充 1-2 个典型场景；每个场景说明背景、用户目标、用户如何一步一步完成目标、过程中触发哪些功能需求、输入输出如何流转、人工确认/失败/权限/审计等边界如何处理。

PRD 场景、功能和用户故事要丰满生动但不失精炼。所有内容必须基于产品体系规划、现有代码和已确认能力，不得把 mock、readiness、sandbox、规划中能力写成真实生产完成。

## Design 质量要求

Design 必须能回答：技术栈如何复用、模块如何分工、数据和状态如何流转、失败如何恢复、关键取舍是什么。

## Plan / Roadmap 质量要求

- Plan 先给出总阶段路线图，再写阶段详情；每个阶段覆盖"阶段六要素"（见 AGENTS.md §2「通用功能开发流程」第 6 步）。计划采用"阶段 → 功能模块 → 工作包 → 可执行切片 → 验收 → 测试 → 文档/回退"的分层执行文档，不以表格为主。
- Roadmap 提供全周期全景图，说明 Now / Next / Later 或 Phase 0 → Phase N 的递进关系。
- **路线图文档顶部必须按以下顺序优先放三块内容**：
  1. **完整功能链路状态**：先写用户目标链路，逐环节说明输入、输出、接线、验证和阻断，并给出整链最低状态。
  2. **完整路线图总览**：列出所有阶段、主题、当前状态和一句话说明。
  3. **下一阶段优先实施内容**：说明下一阶段补齐哪个链路环节、验收标准和风险，不要把下一步埋在长文末尾。

## PRD vs Design 边界

文档内容严格归位，分界以本节为准：

- **PRD**（What & Why）：产品定义、用户故事、功能清单（用户视角）、业务流程、用户交互流程、业务对象（概念层）、非功能需求、验收标准。不含技术栈、字段级模型、API 设计、内部算法。
- **Design**（How）：技术栈选择及理由、系统架构、数据模型（字段级定义）、接口设计、核心算法、系统执行流程、状态流与恢复流程、错误处理与安全、设计决策及备选方案否决理由。

## 顶层文档 vs 功能文档边界

- 顶层 PRD、设计、路线图文档只保留产品级、系统级和版本级摘要。
- 复杂功能的细节必须放到 `docs/features/<feature>/`，顶层文档只保留摘要和链接。
- 系统采用技术栈、全局架构图和全局模块边界放在顶层设计文档。
- 单个复杂功能的模块结构图、流程图、状态机、数据流和事件流放在对应 feature design。
- 开发阶段路线图放在 feature plan；产品全周期路线图放在 feature roadmap，并在顶层 roadmap 中保留摘要。

完整上下文与可追踪性（需求 ID 贯穿）的总则见 AGENTS.md §3「文档边界与质量」，此处不重复。
